# _AUTHORING — 하네스 작성 규칙 (단일 출처)

본 문서는 이 저장소의 md 하네스(CLAUDE.md + `docs/` + `.claude/commands/`)를 작성·유지하는
규칙의 **단일 출처**입니다. 다른 모든 문서·커맨드는 이 규칙을 따릅니다. 새 도메인 문서나
커맨드를 쓰기 전에 본 문서를 읽으세요.

이 문서는 [완성]본입니다 — 그대로 쓰되, 프로젝트 고유 규칙이 생기면 덧붙이세요.

---

## 1. 3계층 책임 분리

| 계층 | 파일 | 역할 | 답하는 질문 |
| --- | --- | --- | --- |
| 라우터 | `CLAUDE.md` | always-on 트리거 라우팅 | "무엇을 건드리면 어디를 보나" |
| 개념·계약 | `docs/*.md` | 도메인별 계약·불변식·시멘틱 | "왜 그런가 / 무엇이 규칙인가" |
| 절차 | `.claude/commands/*.md` | 자기완결적 step-by-step | "어떤 명령을 어떤 순서로 치나" |

각 계층은 자기 역할의 정보만 보유합니다. 이게 깨지는 순간(절차가 docs 로, 개념이 commands 로)
중복이 생기고 유지보수가 무너집니다.

## 2. 단일 출처(SoT) 위임

같은 사실은 한 곳에만 적고, 다른 곳은 **포인터**로 가리킵니다.
- 좋음: "응답 코드 표는 `docs/rest_api.md` §4 참고."
- 나쁨: 같은 응답 코드 표를 3개 문서에 복붙.

새 `##` 섹션을 추가하기 전에, 인접 문서에 같은 주제가 이미 있는지 grep 하세요(§7).

## 3. 계약 파일 (contract files)

플랫폼 전체의 인터페이스를 정의하는 파일들. **확장이 아니라 플랫폼 변경일 때만** 수정합니다.
- CLAUDE.md "계약 파일" 절에 목록화하고, 각 항목에 "상세: `docs/<...>.md`" 포인터를 답니다.
- 같은 glob 을 `.claude/contract_files.txt` 에 적으면 `contract_guard` 훅이 편집 시 경고합니다.
- 디스패처/팩토리류는 "신규 추가 시 분기 추가만 허용, 기존 분기 수정 금지" 규약을 명시합니다.

## 4. Additive 확장 철학

확장은 **기존 파일 수정 < 새 파일 추가** 로 설계합니다.
- 새 종류(backend/processor/adapter…)는 새 파일 + 디스패처에 한 줄(enum + map 엔트리)로 끝나게.
- 이 형태가 가능하도록 인터페이스(ABC)와 디스패처(map)를 분리해 두는 것이 계약 파일의 목적입니다.
- "batch → 결과" 같은 기존 봉투에 맞지 않는 입력/출력 모델은 additive 확장이 아니라
  **플랫폼 변경**으로 다룹니다(별도 절차).

## 5. 자기완결적 커맨드 + 안정 step 앵커

- 커맨드(`.claude/commands/*.md`)는 그 하나만 읽고도 작업을 끝낼 수 있어야 합니다.
- step 에 `§1, §2 …` 안정 앵커 번호를 답니다. 다른 커맨드/문서가 이 번호를 인용합니다.
- **번호를 재배치하지 마세요.** 새 step 은 끝에 append, 세부는 `§3.1` 처럼 하위 번호로.
- 커맨드는 "왜"를 설명하지 않습니다 — 근거가 필요하면 `근거: docs/<file>.md §N` 포인터만.

## 6. 검증 규율

- **실제 실행 환경에서** 검증합니다(컨테이너/실서비스 기동). 호스트 직접 실행·단위 테스트
  단독 종료 금지 — 환경 의존성으로 거짓 통과/실패가 납니다.
- 비동기 기동이면 "기동 성공"으로 보고하기 전에 **헬스 라인을 직접 확인**(로그/엔드포인트).
- 실패 시 환경을 즉시 파괴하지 말 것(로그 확인 기회 상실). 응답 코드는 추측 말고 표로 진단.
- 검증 절차는 커맨드에 두고, 변경 범위별로 분기(`/verify` 단독 ↔ `/verify-e2e` 통합).

## 7. md 모듈성 자기 점검

아래 4종 수정은 시작 전 3계층 분담을 깨지 않는지 확인(그 외는 생략):
1. 새 `##` 섹션 추가 → 인접 md 에 같은 주제 grep.
2. commands 에 개념 설명 추가 → docs 로 옮기고 포인터만.
3. docs 에 step 절차 추가 → commands 로 옮기고 시멘틱만.
4. CLAUDE.md 문단 추가 → 트리거 한 줄 + 문서 위임으로 대체.

## 8. 현재-상태 원칙 (no-legacy)

- md·주석(docstring 포함)은 **현재 구현만** 기술. 로직 변경 시 관련 서술을 같은 작업에서
  완전히 교체하고 옛 동작의 흔적("예전엔/구 방식/~로 변경됨")을 남기지 않습니다.
- 변경 이력의 단일 출처는 git 커밋 메시지입니다.
- 예외: 코드가 *지금도 지원하는* 하위호환 동작의 명세는 현재 기능 문서이므로 유지
  (그 코드가 제거되면 명세도 함께 삭제).

## 부록 A — 새 개념 문서 만들 때

1. `docs/_TEMPLATE.md` 복사 → `docs/<도메인>.md`.
2. 맨 위 **트리거 박스** 작성(어떤 파일을 건드릴 때 읽어야 하는가).
3. CLAUDE.md 라우팅 표에 같은 트리거 한 줄 추가.
4. 컴포넌트 표 / 계약 / 불변식 / 실패 모드 / 관련 문서 순으로.
5. "어떤 명령을 친다"는 적지 말 것 — 커맨드로 위임(포인터).

## 부록 B — 새 커맨드 만들 때

1. `commands/_TEMPLATE-command.md` 복사 → `commands/<동사-목적>.md`.
2. 입력 인자 → 안정 앵커 step(§1, §2 …) → 헬스/검증 → 보고 순.
3. 개념적 "왜"는 적지 말 것 — `근거: docs/<file>.md §N` 포인터만.
4. CLAUDE.md 의 검증/확장 절차 매핑에 한 줄 연결.
